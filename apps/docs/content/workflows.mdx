# Workflows Module Recipe

The Workflows module is the admin surface for the workflow engine of your DaaS
backend. A **definition** is a state machine: states, and commands that move an
item from one state to another. An **assignment** says which definition the
items of a collection get. An **instance** is one item on its way through its
workflow.

The module gives you six screens:

- **`WorkflowsManager`** — the `/workflows` list: search by name or
  description, pagination, and permission-gated create, edit and delete.
- **`WorkflowDetail`** — the `/workflows/[id]` editor: name, description,
  statistics, a states overview, and the state machine drawn as a diagram.
  States and commands are edited in dialogs or directly on the canvas. The
  whole machine is one `workflow_json` document, saved with one request.
- **`WorkflowAssignmentsManager`** — the `/workflow-assignments` list: which
  workflow runs on which collection, and whether a filter rule narrows it.
- **`WorkflowAssignmentDetail`** — the `/workflow-assignments/[id]` form: the
  workflow, the collection, and an optional filter rule edited as JSON.
- **`WorkflowInstancesManager`** — the `/workflow-instances` list (read-only):
  search by collection, state or item id.
- **`WorkflowInstanceDetail`** — the `/workflow-instances/[id]` page
  (read-only): the instance's fields, its workflow as a diagram, and the whole
  transition history, newest first.

This module administers workflows. The button that runs a command on one item
is a different component: the `workflow-button` interface
([Component Map](/components)).

## Install

<Steps>

### Add the module

```bash copy
buildpad add workflows-routes
```

This copies:

- six page shells into `app/[lang]/(authenticated)/workflows/`,
  `workflow-assignments/` and `workflow-instances/`;
- the components into `components/ui/workflow-management/` (22 files);
- the `vtable` component into `components/ui/`, when the app does not have it;
- the workflow hooks, types and editor logic into `lib/buildpad/`.

It also adds **Workflows**, **Workflow Assignments** and **Workflow
Instances** to the sidebar under an **Automation** group
(`components/layout/navigation.ts` — see
[App Shell](/app-shell#customizing-the-navigation--brand)). Entries are matched
by href, so a second run does not duplicate them and your edits stay.

The sidebar labels are dictionary keys: `app.nav.workflows`,
`app.nav.workflowAssignments`, `app.nav.workflowInstances`, and
`app.nav.automation` for the group. A new app has them. An app created before
this module gets them with `buildpad upgrade i18n`; until then the sidebar
shows the English labels.

To install only the components, without pages or sidebar entries:

```bash copy
buildpad add workflow-management
```

### Install the diagram library

The diagram is drawn with [React Flow](https://reactflow.dev)
(`@xyflow/react`, MIT). In a terminal, `buildpad add` offers to install it,
pinned to `^12.9.3`, before it validates the app.

Without a terminal (CI, a script, a coding agent) `buildpad add` does not
install anything it cannot ask about: it prints the command below and its
validation then fails on the missing module. In that case install the library
first, then add the module:

```bash copy
pnpm add "@xyflow/react@^12.9.3"
```

You do not import its stylesheet. `workflow-diagram.tsx` imports
`@xyflow/react/dist/style.css` itself.

### Point the app at your DaaS

The module has no proxy routes. The browser calls the DaaS directly: every
request goes to the URL in `NEXT_PUBLIC_BUILDPAD_DAAS_URL`, with the session
token that `DaaSProviderWrapper` supplies.

```bash filename=".env.local"
NEXT_PUBLIC_BUILDPAD_DAAS_URL=https://your-daas.example.com
```

Because the calls are cross-origin, the DaaS must allow your app's origin
(its `CORS_ORIGINS` setting). Without that, every list shows its load-error
state.

</Steps>

## The routes

Six files give you the whole module:

```
app/[lang]/(authenticated)/
├── workflows/
│   ├── page.tsx            # /workflows                  — WorkflowsManager
│   └── [id]/page.tsx       # /workflows/[id]             — WorkflowDetail (use /workflows/new to create)
├── workflow-assignments/
│   ├── page.tsx            # /workflow-assignments       — WorkflowAssignmentsManager
│   └── [id]/page.tsx       # /workflow-assignments/[id]  — WorkflowAssignmentDetail (use /workflow-assignments/new to create)
└── workflow-instances/
    ├── page.tsx            # /workflow-instances         — WorkflowInstancesManager
    └── [id]/page.tsx       # /workflow-instances/[id]    — WorkflowInstanceDetail
```

The components do not navigate. Each page passes router callbacks, so your
router (and its locale prefix) decides where a click goes.

<Steps>

### The list views

Each list page renders its manager wired to the router. A click on a row opens
the detail page. The create button navigates to the `new` route.

```tsx filename="app/[lang]/(authenticated)/workflows/page.tsx" copy
"use client";

import React from 'react';
import { useLocaleRouter } from '@/lib/i18n/navigation';
import { WorkflowsManager } from '@/components/ui/workflow-management';

export default function WorkflowsPage() {
  const router = useLocaleRouter();

  return (
    <WorkflowsManager
      onWorkflowClick={(workflow) => router.push(`/workflows/${workflow.id}`)}
      onCreateWorkflow={() => router.push('/workflows/new')}
    />
  );
}
```

The assignments page is the same with `onAssignmentClick` and
`onCreateAssignment`. The instances page has only `onInstanceClick`: instances
are created by the backend and change only through a transition.

A row opens for every user who can read the list. A user without update access
gets the detail page read-only.

A load that fails is never drawn as an empty list. A refusal draws an
access-denied state. Any other failure draws a load-error state with the
server's message, and a notification. A failed delete keeps the confirm dialog
open and shows the server's message, so the user can retry or cancel. After a
delete empties the last page, the list loads the page before it.

### URL state (shareable views)

The three lists keep their search and page in the query string by default —
`?search=…&page=2` — so a view can be shared, reloaded or bookmarked. Writes
replace the current history entry and wait for the 300 ms search debounce.
Defaults (empty search, page 1) stay off the URL.

In a Next.js App Router app the writes go through `router.replace`, which the
`DaaSProviderWrapper` template registers with `registerUrlStateWriter`. This
is required there. If you have customised `DaaSProviderWrapper`, keep that
registration.

Turn it off for an embedded list with `urlParams={false}`. Use
`urlParamPrefix="wf-"` when two lists share one page.

### The detail views

A detail page reads the route parameter and passes it as `id`. For
definitions and assignments, `id="new"` means create.

```tsx filename="app/[lang]/(authenticated)/workflows/[id]/page.tsx" copy
"use client";

import React, { use } from 'react';
import { useLocaleRouter } from '@/lib/i18n/navigation';
import { WorkflowDetail } from '@/components/ui/workflow-management';

export default function WorkflowDetailPage({
  params,
}: {
  params: Promise<{ id: string }>;
}) {
  const { id } = use(params);
  const router = useLocaleRouter();

  return (
    <WorkflowDetail
      id={id}
      onBack={() => router.push('/workflows')}
      onSaved={() => {
        if (id === 'new') router.push('/workflows');
      }}
    />
  );
}
```

<Callout type="warning">
**Navigate after a create.** A detail component does not change its own `id`.
After a successful create it still holds `id="new"`, and a second Save would
create a second record. `onSaved` receives the saved record with its new id.
Navigate there to the list (as the generated pages do) or to
`/workflows/${workflow.id}`.
</Callout>

The generated pages follow the reference admin UI: the definition editor
returns to the list after a create and stays open after an update; the
assignment form returns to the list after every save.

`onBack` is called by Cancel, by the breadcrumb, and by the Back button of the
not-found, access-denied and load-error states. Without `onBack` none of those
controls is drawn.

</Steps>

## The editor

- A state is dragged by its grip. A click on a state card only selects it.
- A state is edited from its menu. A command is edited by a click on its row
  or on its arrow.
- A command is added by dragging from a blue dot of one state to another
  state. The Command dialog opens with the target filled in.
- A command is also added from the state's menu (Add Command). The Command
  dialog then asks for the target. This is the way to add a command with the
  keyboard: a connection can only be drawn with a pointer.
- An arrow can be moved to another state.
- Backspace or Delete removes the selected state or command from the
  document. The last state cannot be deleted.
- An end state has no outgoing commands. Its dots start no connection, an
  arrow cannot be moved to start from it, and End State cannot be turned on
  for a state that has commands.
- Save Changes is disabled while there is nothing to save. An update sends
  only the keys that changed.

A command is saved on top of the stored command, so keys the dialog has no
field for are kept.

An action's Parameters must be a JSON object. Text that is not JSON, and JSON
that is not an object (`[]`, `123`, `"x"`), is refused on the field. The save
opens the tab and the action that hold it. An empty field means no parameters.

A definition can be answered without its `workflow_json`, when the user's read
grant on `daas_wf_definition` leaves that field out. The editor then shows a
notice in place of the statistics and the diagram. It does not draw an empty
machine, and it never sends the document. The name and the description can
still be saved.

## The data layer

The screens are thin. The work is in three hooks that you can use anywhere
under `DaaSProvider`.

```tsx
import { useWorkflowDefinitions, DaaSRequestError } from '@/lib/buildpad/hooks';

const { fetchDefinitions, getDefinition } = useWorkflowDefinitions();

const { items, total, totalPages } = await fetchDefinitions({ search: 'approval', page: 1, limit: 25 });
```

Each hook returns `loading`, `error` (the last failure's message),
`errorInfo` (the same failure as a `DaaSRequestError`), and its methods:

| Hook | Route | Methods |
|---|---|---|
| `useWorkflowDefinitions` | `/api/workflows` | `fetchDefinitions(params)`, `fetchAllDefinitions({ search? })`, `getDefinition(id)`, `createDefinition(data)` → the new id, `updateDefinition(id, data)`, `deleteDefinition(id)` |
| `useWorkflowAssignments` | `/api/workflow-assignments` | `fetchAssignments(params)`, `getAssignment(id)`, `createAssignment(data)` → the stored row, `updateAssignment(id, data)` → the stored row, `deleteAssignment(id)` |
| `useWorkflowInstances` | `/api/workflow-instances` | `fetchInstances(params)`, `getInstance(id)`, `fetchInstanceHistory(instanceId)` → every transition, newest first |

A list method takes `{ page?, limit?, search? }` (defaults: page 1, 25 rows)
and resolves to a `WorkflowListResult<T>`:

```ts
interface WorkflowListResult<T> {
  items: T[];         // rows of this page
  total: number;      // rows matching the request across all pages
  totalPages: number; // at least 1
  page: number;       // page that was served
  limit: number;      // page size that was served
}
```

Four details matter when you call the hooks yourself:

- `fetchDefinitions` returns one page. For a picker, use
  `fetchAllDefinitions`, which reads every page.
- `updateDefinition` resolves to nothing. Read the definition again with
  `getDefinition` when you need the stored form. `description: null` clears
  the description.
- A `WorkflowDefinitionRecord` has no `workflow_json` when the caller's grant
  withholds that field. This is not an empty machine: do not draw one, and do
  not send one back.
- `deleteDefinition` is refused (`kind: 'invalid'`) for a definition that is
  assigned to a collection or has instances. The message says which.

### Typed errors

Every method rejects with a `DaaSRequestError`. It is an `Error` whose
`message` is a readable sentence, with three more fields:

| Field | Value |
|---|---|
| `kind` | What the failure means; branch on this |
| `status` | The HTTP status, or `null` when the request got no answer |
| `code` | The backend's error code (`NOT_FOUND`, `FORBIDDEN`, `MFA_REQUIRED`, …), or `null` |

| `kind` | Meaning |
|---|---|
| `notFound` | The record does not exist, or the caller's row rule hides it (404). Also an id that is not a valid id |
| `forbidden` | The caller may not do this (403) |
| `mfaRequired` | The session must pass a second factor first (403 with code `MFA_REQUIRED`) |
| `unauthenticated` | No valid session (401) |
| `invalid` | The request was refused as sent (400, 409, 422). `message` says why |
| `failure` | Anything else: a 5xx, a network error, an answer that is not what the route promises |

```tsx
try {
  const instance = await getInstance(id);
} catch (err) {
  if (err instanceof DaaSRequestError && err.kind === 'notFound') {
    // draw a not-found state
  }
}
```

A failed load never resolves to an empty list, and a `get` never resolves
without a record.

### Editor logic

The functions that build and check a `workflow_json` document are pure and
live in `@/lib/buildpad/utils`: `buildWorkflowCommand`, `buildWorkflowState`,
`applyWorkflowCommandSave`, `applyWorkflowStateSave`, `removeWorkflowState`,
`removeWorkflowCommand`, `moveWorkflowState`, `reconnectWorkflowCommand`,
`findWorkflowCommandProblem`, `findWorkflowStateProblem`,
`findWorkflowConnectionProblem`, `findWorkflowDefinitionProblem`,
`normalizeWorkflowJson`, `isWorkflowFilterRule` and `parseWorkflowFilterRule`.
Use them when you write a custom editor, so your saves keep the keys your
form does not show.

## Permissions

The checks use the collection names both backends enforce. They are exported
from `@/lib/buildpad/types` as `WORKFLOW_COLLECTIONS`.

| Collection | Holds | What the UI does with it |
|---|---|---|
| `daas_wf_definition` | Workflow definitions | `WorkflowsManager` shows Add, Edit and Delete with `create`, `update` and `delete`. `WorkflowDetail` is read-only without `update`, and draws access-denied on `/workflows/new` without `create` |
| `daas_wf_assignment` | Assignments of a workflow to a collection | The same gates on `WorkflowAssignmentsManager` and `WorkflowAssignmentDetail` |
| `daas_wf_instance` | One instance per item | No check in the UI. The API's answer decides: a refusal draws the access-denied state |
| `daas_wf_history` | The transitions of an instance | No check in the UI. Without read access the history card of `WorkflowInstanceDetail` says the history cannot be read |

- The gates come from `usePermissions().canPerform(collection, action)`.
  Administrators pass every gate.
- The gates only hide controls. The API enforces the same collections, so a
  hidden button is not the protection.
- Gate your navigation links too, so a user without read access to
  `daas_wf_definition` does not see the Automation group.
- Two pickers read other collections: the Command dialog's Policies tab reads
  `daas_policies`, and the assignment form's Workflow picker reads
  `daas_wf_definition`. A failed load is a notification, and the stored value
  is kept.

### Who may run a command

A command stores two lists: `policies` (policy ids) and `module_access_keys`.
A caller who holds any listed policy **or** any listed key may run the
command. A command with neither list is open to every authenticated user.

The Command dialog edits `policies`. It has no field for
`module_access_keys`: it keeps the stored keys on save and shows a notice that
the command is gated by them. Set the keys through the API.

## Both backends

The module works against the Next.js DaaS (Supabase) and the Go engine. The
hooks read both pagination vocabularies (`count` / `totalCount` /
`totalPages`, and `meta.filter_count` / `meta.total_pages`), accept
`data: null` as an empty page, and always send `page` and `limit`.

The routes it calls:

- `GET`, `POST` `/api/workflows`; `GET`, `PATCH`, `DELETE` `/api/workflows/[id]`
- `GET`, `POST` `/api/workflow-assignments`; `GET`, `PATCH`, `DELETE`
  `/api/workflow-assignments/[id]`
- `GET` `/api/workflow-instances`, `/api/workflow-instances/[id]` and
  `/api/workflow-instances/[id]/history`
- `GET` `/api/permissions/me` (the gates), `/api/policies` (the Policies tab)
  and `/api/collections` (the Collection picker)

## Prerequisites

- **`DaaSProvider`** above the pages. The module installs under the
  authenticated layout, where `DaaSProviderWrapper` supplies the DaaS URL, the
  session token and the tenant scope header.
- **`<Notifications />`** from `@mantine/notifications` mounted once. Saves,
  deletes and failed loads report through it. The generated root layout
  mounts it.
- **An i18n provider** for a language other than English. The strings are the
  `workflows` namespace, shipped in English and Indonesian. The generated
  `I18nProvider` selects the catalog for the active locale. To change a
  string, set it under `buildpad.workflows` in your dictionary, or pass
  `translations` to one component. Without a provider the components render
  the English defaults.

`pnpm storybook:workflows` (port 6013). The fixture stories run on mock data.
